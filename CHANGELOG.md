First tagged release (in preparation). Adds the custom-puzzle feature suite on top of the generated-puzzle baseline.

### Added — Platform support

- **Supported platforms for this release are Linux and Windows.** Linux ships
  as an AppImage and a Flatpak; Windows ships as an NSIS installer. These are the
  packages attached to tagged releases.
- **Windows requires version 10 1809 (build 17763) or newer, 64-bit.** The floor is
  inherited from Qt 6.8, which the release is built against and which supports
  Windows 10 1809 or later on `x86_64`; older releases of Windows cannot load the Qt
  libraries. The installer checks the Windows build number and stops with a clear
  message rather than installing an application that would fail to start. No
  Visual C++ redistributable is required — the runtime ships inside the installer
  (see *Fixed*), so an offline machine needs nothing downloaded.
- **macOS support is experimental and not shipped in 1.0.0.** The application
  builds and runs on macOS 13+ — an app bundle (`sudoku.app`) with `Info.plist`
  is produced, application data lives in `~/Library/Application Support/Sudoku/`,
  and a Universal Binary (arm64 + x86_64) DMG can be built on demand — but **no
  macOS package is distributed**: without code signing and notarisation (no Apple
  Developer account) a DMG would be unsigned and Gatekeeper-hostile, so the DMG
  job is `workflow_dispatch`-only and is excluded from tagged releases. ARM SIMD
  optimisations are not included (scalar fallback on Apple Silicon). macOS
  packaging may be revisited once signing and distribution are in place.

### Added — UI

- **Separate switches for the board highlights** — the row/column/box highlight and the matching-number highlight are now independent options under Settings → Display, so you can keep the one you use and switch off the one you don't. Both are **on by default**, which is exactly how the board behaved before. "Highlight matching numbers" covers all of it: cells holding the same number as the cell you're on, matching pencil marks, and the pencil mark under the mouse pointer. Together with *Highlight Conflicts* (see Fixed), the three board aids are now independently controllable. Downstream packagers: two new keys `display.highlight_regions` and `display.highlight_same_numbers` in `~/.local/share/sudoku/settings.yaml`, both defaulting to `true` and gracefully ignored by older binaries. No save-format change (`SAVE_FILE_VERSION` stays 1.1).
- **Keyboard input for value / pencil / color, with in-app discovery.** A digit acts on the active input mode (Normal → value, Notes → pencil, Color → color); modifier overrides reach any layer from any mode — `Ctrl`/`Cmd`+digit enters a final value, `Shift`+digit toggles a pencil mark, `Alt`/`Option`+digit (1–6) applies a color — and pressing the same digit again undoes it. Erase follows the same rule: `Ctrl`+`0`/`Delete` clears the value, `Alt`+`0`/`Delete` clears the color, `Shift`+`Delete` clears all pencil marks; `Space` cycles the input mode. The shortcuts are surfaced three ways: the mode button now shows the `Space` cycle key on its face, a new **Help → Keyboard Shortcuts…** dialog lists the full map, and a status-bar hint shows `Ctrl=value · Shift=pencil · Alt=color`. All key combos render per-OS (`⌘/⌥/⇧` on macOS, `Ctrl/Alt/Shift` elsewhere) and every label is translatable. The legacy `A`/`B` color keys and the `N` jump-to-Notes key are retired (covered by `Alt+1`/`Alt+2` and `Space`), keeping the gameplay keyboard layer language-neutral.
- **Cell coloring is now optional** — a new *Enable cell coloring (Color input mode)* switch under Settings → Display turns the manual cell-color layer on or off. It is **on by default**, exactly as the app behaved before. With it off, `Space` switches between values and pencil marks only, `Alt`+digit and `Alt`+`Delete` do nothing, and the mode button, status-bar hint and Keyboard Shortcuts dialog stop mentioning colors — so the feature disappears completely instead of leaving dead keys behind. Switching it off clears any colors currently on the board (cell colors were always transient — they are never written to a save), and switching it back on restores the feature immediately, no restart. Training mode keeps its own coloring either way. Downstream packagers: one new key `display.enable_cell_coloring` in `~/.local/share/sudoku/settings.yaml`, defaulting to `true` and gracefully ignored by older binaries. No save-format change (`SAVE_FILE_VERSION` stays 1.1).
- **Session timer (right of status bar)** — optional indicator showing total time since the app launched, intended as a reminder for long sessions. Toggle via Settings → Display → *Show session timer*. Off by default. Independent of the per-puzzle timer on the left; keeps ticking through menus and pauses. Persists as `display.show_session_timer` in `~/.local/share/sudoku/settings.yaml` (downstream packagers: new YAML key, default `false`, gracefully ignored by older binaries).
- **Pause mode** — a **Pause** button in the action-button row and a **`P`** keyboard shortcut stop the puzzle timer and hide the board behind an opaque "Paused" overlay, so you can step away without your time counting and without being tempted to keep studying the grid. The single control toggles Pause ⇄ Resume; while paused, board input is ignored and a click (or `P`) resumes exactly where you left off. Paused time does not count toward the play-time limits below, and pausing then closing the app still auto-saves your progress (the exit auto-save now persists a paused, in-progress game). Pause is transient UI state — it is not written to saves, so a reloaded game comes back running (no save-format change). The new shortcut appears in the Keyboard Shortcuts dialog, and the overlay uses palette-derived colors so it stays legible in light and dark schemes.
- **Optional session and daily play-time limits** — set a maximum play time per session and/or per day via Settings → *Time Limits* (all off by default, strictly opt-in). The app shows one early heads-up warning, then auto-saves and closes itself when an active limit is reached; the session limit also starts a configurable cooldown before a new session may begin. Only active play counts (paused/completed time is excluded), and **a restart cannot hand back used-up time**: the daily total and cooldown clock live in a new restart-proof ledger, so closing and reopening the app won't reset your day or skip a break (setting the system clock backward is a known, accepted bypass and is not defended against). Downstream packagers: a new **encrypted** ledger file `~/.local/share/sudoku/play_time.yaml` is written (same `EncryptionManager` AEAD scheme as the existing save/statistics files — XSalsa20-Poly1305 via libsodium, already a dependency; **no new dependency or build/link surface**), plus new `time_limits.*` keys in `settings.yaml`. Both default to off and are gracefully ignored by older binaries; the per-puzzle save format (`SAVE_FILE_VERSION` 1.1) is unchanged.

### Added — Custom puzzles

- **Paste-string import** — paste an 81-character puzzle string (digits + `.`/`0` for empty) into the import dialog. Input is validated, length-checked, capped at 4 KiB, and rejected if it has multiple solutions.
- **Edit mode** — enter givens manually via `Ctrl+E`, commit with the toolbar's *Done Editing* action. Validation, uniqueness, and difficulty rating run at commit time.
- **Copy puzzle as text** — `Ctrl+Shift+C` writes the current puzzle's givens to the clipboard as an 81-character string (companion to paste-import).
- **Find step by technique** — pick a specific solving technique (e.g. X-Wing, Naked Triple) and the solver returns the next step in the current board that uses it. Read-only; does not consume a hint credit.
- **Automatic difficulty rating** for imported and edited puzzles. Generated puzzles already arrive pre-rated; imported/edited puzzles now do too, populating the same UIState fields (`puzzle_rating`, techniques, requires-backtracking) so statistics and save files capture an accurate rating.

### Changed

- **Windows now installs per user to `%LOCALAPPDATA%\Programs\Sudoku`, without asking for administrator rights.** The installer was already meant to be a per-user install, but always requested elevation and then placed the application in `C:\ProgramData\Sudoku` — a location intended for shared application *data*, not programs, and one that is writable by non-administrators. (Cause: NSIS resolves the `$LOCALAPPDATA` shell constant to `%ProgramData%` whenever the installer runs in all-users context, which an elevated installer always does.) The install now goes to the per-user location that modern Windows installers use, needs no UAC prompt, and works on machines where the user is not an administrator. The Start Menu shortcut and the Add/Remove Programs entry are registered for the installing user. **This holds even if the installer is started elevated** (right-click → *Run as administrator*, or an account with UAC switched off): it stays a per-user install rather than relocating itself under `%ProgramData%`, which would otherwise place the bundled runtime libraries in a directory any non-administrator can write to — a directory an administrator later loads DLLs from. Uninstalling is pinned to the same location, so an elevated uninstall can no longer leave a dangling Add/Remove Programs entry behind. **Upgrading from 1.0.0-rc1: uninstall it first.** A per-user install cannot see the machine-wide entry rc1 created, so it will not replace it — leaving the old `C:\ProgramData\Sudoku` tree and its Add/Remove Programs entry behind. Saved games, statistics and settings are unaffected: they live in `%APPDATA%\Sudoku` and are not touched by installing or uninstalling.
- **Windows: the installer no longer offers to launch the app on its finish page.** The checkbox started the app as a child of the installer, so it inherited the installer's privileges; an elevated setup meant the first run wrote its settings and saves into the administrator's profile instead of the user's. Start the app from the Start Menu shortcut.
- **Manual saves now use a faster key-derivation cost, and the save list no longer freezes the app.** Opening a save or load dialog — and, before this release, *every application launch* — decrypted each save file to read its name and details, deriving an encryption key per file at a cost of roughly 0.2 s each, twice over, because every candidate file was parsed two times. With a dozen saves that was a multi-second freeze; because nothing limits how many saves you keep, it grew without bound (measured: ~4.7 s at 12 saves, ~19.6 s at 100). Three changes fix it: each file is parsed once instead of twice; new encrypted files share a per-machine key derivation instead of forcing a separate one per file; and the derivation cost tier for manual saves moves from MODERATE to INTERACTIVE (the tier the statistics and play-time files already use). Saves written by earlier versions still load — the cost tier is recorded in each file and honoured on read. **Note:** saves created *before* this release keep their original per-file key derivation, so they still cost roughly 0.2 s each to list until they are next re-saved; the speed-up applies fully to saves written from this release onward. **Downstream packagers: no format version change** (`SAVE_FILE_VERSION` stays 1.1) and no new dependency; the bytes inside newly written encrypted saves change, but the file layout does not.
- **Renaming or importing a save keeps it encrypted.** Both paths previously re-wrote the file with default settings, which silently turned an encrypted save into a plaintext one. Creating, renaming, and importing a save now all apply the same policy, so every manual save in the save directory is encrypted. Renaming a plaintext save therefore encrypts it — deliberately, and never the reverse. **Export is unchanged and still writes a portable plaintext file on purpose**, because encryption is bound to the machine that wrote it.

- **Repository renamed** from `sudoku-cpp` to `sudoku` (GitHub URL is now `https://github.com/darkstar79/sudoku`; the old path redirects). Downstream packaging recipes that fetch source by URL should switch to the new path.
- **Reverse-DNS app ID** changed from `org.sudoku_cpp.Sudoku` to `io.github.darkstar79.Sudoku` (follows Flathub naming convention for GitHub-hosted projects without a custom domain, derived from the new repo name). The `.desktop`, AppStream metainfo, and SVG icon files are renamed in lockstep; downstream `.spec` and packaging recipes that hardcode the old paths or `Icon=` value need to be updated.
- **Bundled dependencies bumped** for the Flatpak module set and the Conan recipe used by the Windows build: libsodium `1.0.18` → `1.0.21`, yaml-cpp `0.8.0` → `0.9.0` (Conan recipe was already at parity-via-Flatpak for yaml-cpp; both now align).
- **fmt bumped from `11.2.0` to `12.1.0`** in the Conan recipe (`conanfile.py`). On macOS, Qt6 from Homebrew adds `/opt/homebrew/include` as a system include path, which exposes `fmt/12.1.0` headers to the compiler; linking against a Conan-built `fmt/11.2.0` then produced `fmt::v12` unresolved symbols. The bump aligns the Conan dependency with what Homebrew ships, and is benign on Linux/Windows (spdlog 1.15.3 is API-compatible with fmt 12.x via `SPDLOG_FMT_EXTERNAL`). Downstream OBS/Flatpak packagers that provide their own `fmt` are unaffected.
- **Save file format** bumped from 1.0 → 1.1. A new `PuzzleOrigin` field records whether a puzzle was generated, paste-imported, or entered in edit mode. Loading older 1.0 saves remains supported; missing field defaults to `Generated`.
- **Save files now carry a `rating_model_version` key** (additive; schema stays at 1.1). It records which rating-model version produced a save's stored rating/difficulty so the rating model can evolve in future releases without ever silently reclassifying an existing save: on load the stored rating is always kept as-is (never recomputed), and a save rated by a different model version is flagged stale for an optional, user-triggered re-analysis. The save loader also now reads the schema `version` key (previously write-only); unrecognized future versions load best-effort. Older saves without the new key load unchanged (treated as model version `0`). Downstream packagers: new optional YAML key, gracefully ignored by older binaries.
- **Three advanced-technique difficulty ratings corrected** for closer Sudoku Explainer alignment: Empty Rectangle 4.5 → 4.3, ALS-XZ 7.5 → 6.8, Sue de Coq 7.5 → 6.6. As a result, a newly generated, imported, or edited puzzle whose hardest required technique is **ALS-XZ** or **Sue de Coq** is now labelled **Expert** instead of **Master** (both corrections cross the 7.5 threshold); the Empty Rectangle change stays within Hard and reclassifies nothing. **Existing saved games are unaffected** — a save's stored rating and difficulty are snapshot-preserved on load and never recomputed, so no save is silently reclassified; the rating model bumps from version 1 to 2 (`rating_model_version`), and saves rated by the older model are flagged stale for optional, user-triggered re-analysis. Downstream packagers: no install-tree impact; newly written saves carry `rating_model_version: 2`.
- **Difficulty rating is now context-sensitive per step** — a technique's Sudoku Explainer rating can vary with the individual step rather than being one flat value per technique. The first technique to use this is **Hidden Single**, which now rates **1.2** when the digit is confined to a 3×3 block (SE's easier "block" case) and **1.5** when it is confined only to a row or column, matching Sudoku Explainer v1.2.1. Both values sit inside the **Easy** band (`[0, 2.5)`), so **no puzzle changes difficulty bucket** and **no saved game is reclassified** (stored ratings are snapshot-preserved on load, never recomputed, exactly as for the corrections above). The rating-model version is intentionally **left at 2** — this is a pre-1.0.0 model refinement with no shipped saves to protect. Downstream packagers: no install-tree, save-format, or `rating_model_version` impact.
- **Full House and "Direct" placement forms are now rated faithfully (SE v1.2.1).** A **Full House** — the last empty cell in a box, row, or column — is now recognised as its own technique rated **1.0** (Sudoku Explainer's easiest "Last value" case) instead of being mislabelled a Naked Single (2.3). It is also a new **trainable technique** and the first rung of the Training-mode learning path, appears by name in hints and the *Find Step by Technique* dialog, and adds one save-pinned technique id (appended after the existing ids, never renumbering them). In addition, the placement-forcing **"Direct"** forms now rate lower than their elimination-only counterparts when a step's own eliminations force a placement: Direct Pointing **1.7** (vs 2.6), Direct Claiming **1.9** (vs 2.8), Direct Hidden Pair **2.0** (vs 3.4), Direct Hidden Triplet **2.5** (vs 4.0). For a **newly generated, imported, or edited** puzzle whose single hardest step is one of these forms, the puzzle can now land in an easier difficulty band. **Existing saved games are unaffected** — stored ratings are snapshot-preserved on load and never recomputed — and the rating-model version is intentionally **left at 2** (pre-1.0.0 model refinement, no shipped saves to protect). Downstream packagers: a new translatable string **"Full House"** plus its explanation copy is added (new `.ts` source entries to translate); no install-tree or `rating_model_version` impact.
- **Difficulty rating now scales with fish size and chain length.** Techniques whose difficulty genuinely grows with the size or length of the pattern now compute `base + 0.1 × (size/length above the smallest case)` instead of one flat value, so a **larger fish or longer chain rates strictly higher** than a smaller/shorter one of the same technique (Sudoku Explainer's structural scaling). This affects the multi-size fish (Franken / Mutant / Kraken Fish), the X-chains and X-cycles (XY-Chain, X-Cycles, Grouped X-Cycles), and the AIC nice-loops (Nice Loop, Continuous Nice Loop, Grouped Nice Loop); the smallest case of each reproduces its previous flat rating exactly. The length term is bounded so the hardest in-practice family, **XY-Chain (6.6)**, tops out at **7.1** for the longest chains generated — staying inside **Expert** by construction and never crossing into Master. A fixed-seed corpus (140 Hard/Expert/Master puzzles) confirmed **0 puzzles change difficulty bucket** under the new model. **Existing saved games are unaffected** — stored ratings are snapshot-preserved on load and never recomputed — and the rating-model version is intentionally **left at 2** (pre-1.0.0 model refinement, no shipped saves to protect). Downstream packagers: no install-tree, save-format, or `rating_model_version` impact.
- **Solver gains budget-bearing overloads** — `solvePuzzle(board, std::chrono::milliseconds)` and a technique-targeted dispatch. The backtracking fallback now honors the deadline so adversarial inputs cannot hang the UI.
- **Hint message clearing** — stale `hintMessage` is cleared on every `getHint` exit path so dismissed hints don't reappear after subsequent moves.
- **Session lifecycle** — entering edit mode finalizes any active statistics session as abandoned (previously orphaned).
- **Language selector** now discovers installed translations automatically. Packagers can ship a new locale by adding `sudoku_<code>.qm` to the translations directory and a matching `.ts` entry in `CMakeLists.txt`; no C++ change is required. Locale codes from `settings.yaml`, the legacy `language.txt`, and the Settings dialog are validated against a BCP 47 subset (`^[a-z]{2,3}(_[A-Z]{2})?$`) before being interpolated into a filesystem path.
- **Determinism hardening across the solver/generator/rater, now enforced by CI.** Every wall-clock and unseeded-RNG bypass in the engine is routed through the injected `ITimeProvider` / a seeded RNG: the backtracking solver takes the clock by injection (deadlines are testable), the rater enforces a solve budget so a no-logical-path board can't livelock generation, and the generator records the **actual** seed it used — so a puzzle generated with a random ("seed 0") seed is now reproducible from its recorded `result.seed` (previously the sentinel `0` was stored and the puzzle could never be reproduced). A new build-failing **Determinism Gate** ([scripts/check_determinism.sh](scripts/check_determinism.sh), CI job `needs: format-check`) rejects new `steady_clock`/`system_clock::now()`, `std::localtime`, or `random_device` calls in `src/` outside the single `ITimeProvider` bridge unless explicitly annotated. The non-reentrant `std::localtime` in the CSV statistics exporter was replaced with the reentrant `localtime_r`/`localtime_s` idiom. Downstream packagers: new dev-only script + CI job; **no install-tree, runtime, or save-format impact**. (#24)
- **The move-history `timestamp` field was dropped from the save format.** It stored a `steady_clock` value that is meaningless across an application restart and had no reader (move order is positional, not time-based). The `timestamp` key is no longer written; the save schema **stays at 1.1** (the key was always optional on read), and older saves that still carry it load unchanged — the key is ignored. Downstream packagers: save-format-tolerant both directions; no version bump. (#24)
- **Release-version integrity is now guarded, and packaging metadata is validated per PR.** A new `scripts/check_release_consistency.sh` cross-checks the version declared in `project(VERSION)` (CMakeLists.txt, the single source of truth) against its two hand-maintained mirrors — `version` in `conanfile.py` and the top `<release>` entry in the AppStream metainfo — and, on a tag push, that the tag equals `v<PROJECT_VERSION>` (or a `v<PROJECT_VERSION>-rc<N>` pre-release, which skips the date check) and the metainfo release date is within 60 days of the tag commit. `packaging.yml` gains a fast `release-guard` job that runs it before any artifact is built, so a mismatched tag fails in one place and ships nothing. Per-PR CI now runs `appstreamcli validate --no-net` on the metainfo and `desktop-file-validate` on the desktop entry (the same class of check Flathub's buildbot runs). The stale metainfo release date (`2026-03-20`) was corrected. Downstream packagers (all four OBS namespaces and any future Flathub submission): the metainfo/desktop files are now validated in CI; **artifact filenames now carry the version without the leading `v`** — a `v1.0.0` tag produces `Sudoku-1.0.0-x86_64.flatpak`, `Sudoku-1.0.0-x86_64.AppImage`, and `Sudoku-1.0.0-win64.exe`, one identical version string across all packages (REL-3, REL-4). Pre-release tags (`v1.0.0-rc2`) build artifacts too, with the `-rc2` suffix preserved across all names including the Windows installer (`Sudoku-1.0.0-rc2-win64.exe`, via a `cpack -D CPACK_PACKAGE_FILE_NAME` override on tag refs).

### Removed

- **Manual "Analyze Difficulty" menu action.** Auto-rating makes it obsolete — every playable puzzle is now rated at creation time (or loaded with its rating from a save). Retry would have been a placebo anyway since `scoreDifficulty` is deterministic on a given board.

### Security

- **A crafted save file can no longer redirect file operations outside the save directory.** A save's id is read from the file's own contents, and it was concatenated into a path unchecked — so a planted `save_id` such as `../../something` could point a load, delete, or save at a file elsewhere on disk. Save ids are now required to be exactly 16 lowercase hex characters (the form the app generates); anything else is refused before any path is built from it. Legitimate saves are unaffected — every id the app has ever generated satisfies this — and the save format is unchanged (`SAVE_FILE_VERSION` 1.1).

- **Save-file decompression is now capped at 64 MiB.** Previously the zlib decompression loop could allocate up to ~4096× the compressed input before giving up — a crafted 10 MiB save file could demand ~40 GiB of RAM and crash the process via OOM. The cap is far above any realistic save (YAML saves are typically <1 MiB) but small enough to keep the decompressor's memory bounded; oversized inputs are now rejected with `CompressionError`. Affects both regular save loading and `importSave`. (#12)
- **Numeric fields in a save file are now range-validated on load.** A hand-edited or otherwise malformed save could previously carry out-of-range move positions, cell values, or note values that the loader accepted (it checked only board *dimensions*, not the numbers inside); the bad values could then cause an out-of-bounds write when you undid/redid a move, or trigger undefined behavior. Every numeric field — move row/column/value/type, the move index, board cells, and pencil-mark values — is now checked against the board's fixed range at load time, and a save that violates it is refused as invalid data rather than mishandled. A rejected file is preserved aside, never overwritten. Legitimate saves are unaffected and the save format is unchanged (`SAVE_FILE_VERSION` 1.1).

### Fixed

- **"Highlight Conflicts" now actually turns conflict highlighting off.** The Settings → Display checkbox was persisted and restored correctly but never reached the board: a duplicated digit was always drawn in red regardless of the setting. **If you had already unchecked it, the red digits will now disappear** — that is the setting finally taking effect. Conflict *detection* itself is unchanged (hints and validation are unaffected); only the red colouring is now optional. No new settings key — the existing `display.show_conflicts` is unchanged, still defaulting to `true`.
- **The session timer now appears immediately on launch when enabled, and changing the detailed-statistics settings now takes effect immediately instead of on the next launch.** Two settings had drifted in opposite directions: *Show session timer* had an on-change handler but no startup handler, so the status-bar timer stayed hidden after a fresh launch until you re-toggled it in Settings that session; *collect detailed stats* / *encrypt detailed stats* had a startup handler but no on-change handler, so flipping either mid-session did not reach the statistics manager until you restarted. `MainWindow` and `GameViewModel` now each apply their persisted settings through a single function invoked from both the initial apply and the settings-change observer, so a setting wired into one path can no longer be silently missing from the other.
- **Windows: the app no longer crashes on startup on machines with an older Visual C++ runtime.** The installer shipped no C++ runtime of its own, so `sudoku.exe` bound to whatever `MSVCP140.dll` happened to be in `System32`. Binaries built with the Visual Studio 2022 17.10+ toolset require version **14.40 or newer**; on a machine still carrying an older copy (observed: 14.22, from 2019) the process faulted inside the runtime during startup — no window, no error message, and an empty `sudoku_debug.log`, because the crash happened before the first line could be written. The Visual C++ runtime DLLs (`msvcp140*.dll`, `vcruntime140*.dll`, `concrt140.dll`) now travel inside the installer and are loaded from the application directory, so a fresh install works without downloading a redistributable — which matters on machines with no internet access. The Universal CRT is deliberately not bundled: it is an operating-system component on Windows 10 and later, the supported floor. Downstream packagers: Windows-only change, install tree gains the runtime DLLs; the configure step now fails with a clear error if they cannot be located, rather than silently producing an installer without them.
- **Windows: translations and the debug log now work for users whose account name contains non-ASCII characters (umlauts, accents, non-Latin scripts).** Paths coming from Qt were handed to `std::filesystem::path` as UTF-8 bytes, which Windows decodes using the active code page instead — mangling any non-ASCII component. This became reachable with the per-user install location above, because that path contains the account name: on a machine with a profile like `C:\Users\Müller`, the application directory was misread, so the bundled translations were not found (the language list collapsed to English alone) and the debug log was quietly written to `%APPDATA%\Sudoku\logs` instead of next to the executable. Path conversion now uses the platform's native encoding at both places that derive a path from the executable's location. Non-Windows platforms are unaffected — their native path encoding is already UTF-8.
- **A debug log that cannot be created no longer costs you anything but the log.** Logging is configured before the main window exists, so a failure there used to escape as an unhandled exception and end the process with no window and no message — reachable on a read-only or otherwise unwritable install directory. The app now falls back to the per-user data directory (`%APPDATA%\Sudoku\logs`, `~/.local/share/sudoku/logs`), and only if that fails as well does it continue with console-only logging. Note that a Windows GUI build has no console attached, so in that last case no diagnostic is visible anywhere — the application still starts and plays normally.
- **Windows: the executable now reports its real version instead of `0.0.0.0`.** `sudoku.exe` carried an icon but no `VERSIONINFO` resource, so Explorer's *Details* tab, Add/Remove Programs, and Windows Error Reporting showed no usable version — a crash report from the field could not be tied to a build. The resource is generated from `project(VERSION …)` in `CMakeLists.txt`, which remains the single source of truth, so it cannot drift from the release version.
- **Resuming a game now keeps your clock, your hint budget, and your counters — and finishing it counts.** Reopening a save (including the auto-save the app resumes on launch) rebuilt the board but nothing else: the timer restarted at `00:00:00` and the *next* auto-save wrote that zero over the stored time, permanently destroying it — the value the Load dialog had just shown you. The resumed game also began with no statistics session, so the hint button was stuck at 0 remaining and inert, moves and mistakes went unrecorded, and completing the puzzle registered nowhere — no games-completed count, no best time, no streak. Restoring a save now re-seats the elapsed time and the mistake counter, starts a statistics session carrying the save's own difficulty and rating, and seeds it with the moves, hints, mistakes, and play time you had already accumulated. Saves in turn record those counters (the fields existed in the file format but were never written), so the hint budget survives a restart — relaunching no longer hands back spent hints — and a completed resumed game reports its *full* play time rather than only the time since you reopened it. Corrupt/hostile counter values are clamped, so a tampered save cannot mint extra hints. No save-format change: no new keys, no version bump, and older saves load exactly as before (their zero counters simply seed zeros).
- **Lifetime statistics no longer grow every time you quit and resume the same puzzle.** A puzzle played across several sittings was counted once per sitting: each time you reopened it, the play time, moves, hints and mistakes you had already accumulated were added to your lifetime totals *again*, and the puzzle itself counted as another game played. Playing 20 moves over five minutes and then relaunching four times without touching the board reported 100 moves and 25 minutes played, across five games. The inflation compounded with every cycle and, because it was written into the stored session history, it also survived deleting the summary file. Each sitting is now credited only with the play it actually added, and the several sittings of one puzzle count as one game played — so **total time played**, **total moves**, **games played** and the per-difficulty averages in the statistics screen and the CSV export describe your real history. A resumed win still records its *full* time as your best time for that difficulty, not just the closing stretch. **Totals recorded before this release are not corrected**: the stored history from then does not distinguish carried-over progress from new play, so the information needed to undo the inflation was never written down — the numbers stop growing from here, but existing ones keep whatever inflation they picked up. The per-session CSV export gains four **appended** columns — `Carried_Duration_Seconds`, `Carried_Moves`, `Carried_Hints`, `Carried_Mistakes` — so the export stays reconcilable with the statistics screen: each row still reports the puzzle's running totals at the end of that sitting, and subtracting the carried columns gives that sitting's own play. Existing column positions are unchanged. Downstream packagers: session records in `~/.local/share/sudoku/game_sessions.yaml` gain five additive keys, defaulted so that records written by earlier versions read exactly as they do today; older binaries ignore them. No file-format version change, no new dependency, and `SAVE_FILE_VERSION` is not involved.
- **Resetting a resumed game no longer crashes the application.** Pressing **Reset** on a game reopened from a save — including the auto-save the app resumes on launch, so this was the ordinary path of play → quit → relaunch → Reset — killed the process outright, taking with it any progress made since the last automatic save. Reset copied the puzzle's solution to the new board without checking that one existed, and a resumed game carries no solution (it is not stored in save files, and is never recomputed on load). Custom puzzles entered in edit mode were affected identically. Reset now carries the solution over only when the game has one, so a resumed or hand-entered puzzle resets exactly like a generated one: clues restored, entries and pencil marks cleared, timer back to `00:00:00`, hint budget refilled. Mistake highlighting on a solution-less game continues to fall back to duplicate detection, as it already did before the reset.
- **Saving a game no longer produces a file that throws the game away when you open it.** Two kinds of manual save were written correctly, listed correctly in the Load dialog with their real name, time and difficulty — and then, on load, silently replaced with a brand-new random puzzle. Board, pencil marks, elapsed time and remaining hints were all lost, and because the app simply looked like it had started a new game, nothing signalled that anything had gone wrong. It affected **(a)** any game saved after being resumed from a previous session, and **(b)** any game saved when you had entered pencil marks but not yet placed a digit — which included a freshly started puzzle you had only made notes on. Two separate over-eager checks were responsible, both meant to detect a historic save-writing bug. The one behind (a) treated a save with no undo history as suspect, which a resumed game legitimately has, so saves now record whether their history is complete and are judged on what they can truthfully claim. The one behind (b) treated any untouched board carrying pencil marks as suspect; it now tests for the shape that bug actually produced — a board with no cells left to fill, or none filled in at all. Both remain protected against genuinely broken saves, and a puzzle with no empty cells is now refused when you paste or enter it rather than accepted and rejected later. **Note:** manual saves written from a resumed game *before* this release cannot be repaired retroactively — the information needed to tell them apart from a corrupt file was never written into them — so a save taken from a resumed game before you made any further move will still be rejected on load (one taken after any move loaded before and still does). Notes-only saves from before this release load correctly again. Downstream packagers: `SAVE_FILE_VERSION` is unchanged at 1.1. Newly written saves gain one additional boolean key; older binaries ignore it, and saves that lack it are read exactly as before.
- **Toolbar and status-bar text is now legible in dark mode (was light-on-light).** With the desktop in a dark color scheme, the always-visible chrome text — the *Difficulty:* / *Hints:* labels, the difficulty combo, the SE rating link, and the status-bar labels (timer, status, modifier hint, session timer) — inherited the OS palette's near-white text and ghosted against the chrome, whose background is already forced light in both schemes. Each of those widgets now carries an explicit, static dark text color that is legible on the light chrome and unchanged from what light mode already showed. The board stays as before. (A full system-aware dark theme — themed board colors, popups, and live scheme switching — is tracked separately.)
- **Finishing a puzzle no longer reopens it on the next launch.** Completing a puzzle pauses the timer, which gates auto-saving, so the on-disk auto-save kept the board from just before the final move — and a relaunch resumed that almost-finished puzzle instead of starting fresh. The auto-save is now cleared when a game completes, so a finished puzzle is never offered for resume.
- **An in-progress game now reopens on the next launch instead of starting a new one.** Auto-saves are written without move history (by design — `include_history = false`), but `restoreGameState`'s corruption heuristics treated an empty move history as a sign of a broken save and discarded it. As soon as you placed a digit or entered a pencil mark, the heuristic flagged the auto-save as "corrupt" and started a fresh game on restart — so any in-progress puzzle was lost on quit. The two heuristics now apply only to manual saves (which do carry history); auto-saves with real progress resume their board, notes, and hint-revealed cells. Manual-save corruption protection is unchanged.
- **Applying a cell color now updates the board immediately.** Cell colors are rendered but were omitted from `GameState::operator==`, which `Observable<GameState>::update()` uses to decide whether to notify. A color-only change therefore compared "equal", no notification fired, and the board did not repaint until the next unrelated change (a value entry, selection move, etc.) — so `Alt`+digit and plain Color-mode coloring looked like they did nothing. Colors are now part of the equality, so a color change notifies observers and the board repaints at once. Colors remain ephemeral (not saved, not undoable).
- **Master-difficulty saves now load correctly.** Previously the save loader's range check hardcoded `MAX_DIFFICULTY = 3` (Expert), so every Master save (difficulty 4) was silently rejected with `InvalidSaveData` — permanent data loss for Master-difficulty games. The range now tracks the `Difficulty` enum end-to-end. Existing saves that would not load before this fix will load after it. (#11)
- **Master games are now recorded in statistics.** The statistics gatekeeper still enforced the pre-Master upper bound (Expert=3), so every finished Master game was silently dropped — no session record, no games-played/completed count, no best or average time or rating. The bound now tracks the full `Difficulty` enum, so Master games appear in the statistics screen like every other difficulty.
- **Corrupt statistics session files are quarantined instead of corrupting memory.** A `game_sessions.yaml` entry with an out-of-range difficulty value is now rejected at the deserialization boundary and routed through the existing archive-and-recover flow (the file is preserved on disk and moved aside), rather than being indexed into fixed-size aggregate arrays — which was an out-of-bounds write reachable from an on-disk file during normal startup.
- **A failed statistics write no longer discards unsaved sessions, and a transient encryption failure no longer erases the existing history.** When flushing game sessions to disk failed (e.g. a transient write error), the pending sessions were cleared from memory anyway, silently losing games the player had actually finished. Separately, if session encryption failed for one flush, the plain-YAML fallback wrote only the pending sessions and overwrote the entire prior (encrypted) history. The flush now always serializes the full merged history (on-disk + pending) in a single all-or-nothing write: sessions not confirmed written to disk are retained and re-flushed on the next successful write, and the encryption-failure fallback preserves the complete history instead of destroying it.
- **AVX-512 dispatch now requires the BITALG sub-feature.** The solver's AVX-512 path issues `_mm512_popcnt_epi16` (in `findMRVCell`), which requires AVX-512 BITALG — present on Zen 5+ and Ice Lake-SP+, but missing on Skylake-X / Cascade Lake / Zen 4. Previously the dispatch gate only checked AVX-512F + AVX-512BW, so these CPUs were selected onto the AVX-512 path and crashed with SIGILL on first popcount. Detection now reads CPUID(7,0).ECX bit 12 and dispatch falls back to AVX2 (or scalar) when BITALG is absent. (#17)
- **Training-mode statistics now persist for all 54 techniques.** The reverse-lookup loop in `training_statistics_serializer` walked enum values `0..GroupedXCycles` (41) and silently dropped the 12 strategies added at 42–53 on reload (SashimiXWing/Swordfish/Jellyfish, Unit/Region ForcingChain, MutantFish, KrakenFish, ALSChain, JuniorExocet, UniqueLoop, ContinuousNiceLoop, GroupedNiceLoop). Mastery progress for the most advanced techniques was lost across launches. The loop now iterates `kAllTechniques` (the canonical list in `training_learning_path.h`), so future strategy additions are picked up automatically. (#13)
- **MainWindow no longer leaves a dangling subscription on the SettingsManager.** A direct `subscribe(...)` discarded its unsubscribe handle; because `settings_manager_` is a `shared_ptr` held by DIContainer and outlives `MainWindow`, the next `setSettings(...)` could invoke a lambda dereferencing a destroyed `this` (use-after-free on `auto_save_timer_`, `training_mode_action_`, etc.). The subscription is now routed through `observer_` (CompositeObserver) so teardown happens in `~MainWindow`. (#14)
- **AVX-512 ops now use aligned loads to match the alignas(64) contract.** `SIMDConstraintState` is `alignas(64)` and its `candidates` array sits at offset 0, but the AVX-512 entry points (`findMRVCell`, `findNakedSingle`) called `_mm512_loadu_si512` (unaligned). GCC has been observed substituting `vmovdqa64` (aligned) once it infers alignment from surrounding context — an intermittent Release-only SIGSEGV waiting to fire if any caller ever passed an under-aligned buffer. The path now uses `_mm512_load_si512` (matching the AVX2 path's `_mm256_load_si256`) with an `assertSimdAligned()` guard at every entry, plus a Catch2 regression test exercising the AVX-512 entry points on boundary inputs. (#18)
- **"Show conflicts" / "Show hints" toggles and status messages are no longer wiped on every keystroke.** `GameViewModel::updateUIState()` was rebuilding a fresh `UIState` and forwarding only `input_mode` / `notes_filled`, silently resetting `show_conflicts`, `show_hints`, and `status_message` to their defaults on every call (which fires on every move, undo, and completion check). Disabling conflict highlighting via Settings would un-disable itself the moment the user typed anything, and the completion message from `checkSolution` vanished on the next move. The method now mutates the existing state in place so sticky fields survive. (#15)
- **Observable is now safe against reentrant `set`/`update` and against subscribers that unsubscribe during their own callback.** Two coupled hazards in `core::Observable`: (1) the interface-observer notification loop iterated `observers_` directly, so an `IObserver::onNotify` that called `unsubscribe()` (which uses `std::erase_if` on the same vector) invalidated the loop iterator → UB on the next step (callback path was already snapshot-protected; interface path was not); (2) a callback that reentrantly called `set()` mutated `value_` before the outer notification finished, so later subscribers in the same batch silently received the newer value instead of the one that triggered notification. Combined with a callback that destroyed another subscriber (or its parent `View`), this manifested as out-of-order notifications and use-after-free on `[this]`-capturing closures. The fix snapshots both `observers_` and `value_` at the top of `notifyObservers`, gates each invocation on live subscription state (mirroring the callback path's existing guard), and defers reentrant `set`/`update` into a `pending_value_` slot that is drained after the outer notification completes — repeated reentries coalesce to the latest value. Observable's header now also documents the subscriber-lifetime contract. (#16)
- **Pencil marks are no longer corrupted when a placement is undone or cleared.** Placing a number strips it from the pencil marks of its peers; undo (and clear) then had to put those marks back, but `restoreConflictingNotes` re-derived candidates against the live board instead of recording what was actually removed. It over-restored (adding the digit to peers that never had it), under-restored across interleaved place/undo/clear sequences (leaving cells with too few candidates — e.g. three cells in a unit sharing only two values), and `clearCell` restored nothing at all. Each forward placement now records the exact set of peers it stripped the mark from (in the move), and undo/redo/clear replay that delta verbatim, so cleanup and restore are true inverses across value, hint, and clear edits — a manually-eliminated candidate is never resurrected, and clearing a value gives its candidates back to the peers it had blocked. (#76)
- **A corrupt save file is no longer left where the next save could overwrite it.** When the loader hits an unreadable/unparseable save it now archives the original bytes aside as `<file>.corrupt-<timestamp>` (mirroring the existing unreadable-statistics-history recovery) and surfaces a recoverable error, instead of returning an error while leaving the damaged file in place for a subsequent auto-save to clobber. The original bytes are always preserved, never deleted, so a partially-recoverable save can still be salvaged by hand. (#24)
- **"Undo to last valid state" no longer silently leaves a wrong move on the board after a redo-branch was truncated.** `recordMove` truncates the redo tail when the user makes a new move after undoing, but did not clamp `last_valid_state_index_` to the new array end. If the tracked index dangled past the truncated tail, `undoToLastValid` saw `move_history_index_ < last_valid_state_index_`, exited its loop immediately, and reported "Undone to last valid state" while leaving the wrong move on the board. The index is now clamped at truncation, and the undo loop walks back one move at a time (reverting non-hints, stepping past hints) instead of delegating to `undo()` — which could decrement past the target by `1 + N` for `N` contiguous hints. (#15)
- **Kraken Fish steps no longer carry finned-fish eliminations under the wrong technique label.** `tryFinnedPattern` was bundling in-fin-box finned-fish eliminations (`free_elims`) with chain-verified Kraken eliminations into a single SolveStep tagged as Kraken Fish. Because FinnedXWing/Swordfish/Jellyfish run earlier in the strategy chain and already catch those in-box eliminations, the bundled output (1) inflated Kraken's apparent difficulty contribution, (2) made the step's `position` point at a non-Kraken cell, and (3) confused the technique-correctness harness. The step now reports only the chain-verified Kraken eliminations; the in-fin-box ones are left to the finned strategies. (#20)
- **A Kraken Fish whose fin placement self-contradicts now reports the simpler fin-exclusion instead of a vacuous elimination batch.** When placing the digit at the fin cell propagates to a contradiction, the old `verifyKrakenElimination` returned `true` *vacuously* for every candidate target — so the step listed a batch of cover-cell eliminations "verified" by a chain that had actually self-destructed. The explanation was misleading (the chain excluded nothing), and the step was rated as a full Kraken Fish (SE 8.5) despite doing the work of a much simpler deduction, double-counting in the puzzle rater. The fin-placement propagation is now hoisted out of the per-target loop and run once; on contradiction the step reports the strictly stronger, honest conclusion — *the fin cannot hold the digit* — as a single elimination on the fin cell, rated at the underlying finned-fish level (X-Wing 3.4 / Swordfish 4.0 / Jellyfish 5.4) rather than 8.5. Still tagged `KrakenFish` (a fin-exclusion is not a distinct technique in the standard taxonomy). Difficulty ratings of puzzles reachable via this pattern may shift accordingly. (#40)
- **Kraken Fish no longer reports an inverted "elimination" of the digit from a cell its own fin-chain places that digit into.** When the fin-placement chain *forces* the digit into a cover-line target cell (outside the fin's box), the per-target test treated a zeroed candidate mask as "the digit was eliminated here" — but `placeInState` zeroes a *filled* cell's mask, so a cell the chain had just *placed* the digit into satisfied the elimination test and was reported as an elimination of that digit: the exact inversion of reality. Removing the digit from the one cell it must occupy is unsound. The test is now gated to cells still empty after propagation, so a target the chain fills with the digit is suppressed entirely (neither eliminated nor placed — a placement would be sound only under the unproven fin hypothesis, while the elimination's own validity rests on the complementary fish-body case where that cell instead *loses* the digit, so nothing can be concluded about it). The genuine cover eliminations the same pattern yields are unaffected. The normal solve loop rarely surfaces this (Kraken Fish is the last logical strategy tried, so cheaper techniques almost always resolve a cell first), but **Find step by technique** invokes the strategy directly — a user who picked Kraken Fish on an affected board could be told to remove the correct candidate. A corrected ground-truth sweep finds the pattern is common on hard boards, not rare. Difficulty ratings of puzzles reachable via this pattern may shift accordingly. (#59)
- **Junior Exocet strategy rewritten to the sound Bird/Champagne definition.** The previous implementation was a placeholder that searched targets in the *wrong* bands (outside the JE band rather than inside it), accepted targets containing as few as one base candidate, never checked that the two targets sat in different cross-lines, never checked that the union of target candidates covered the base set, and skipped the S-cell cover-house invariant entirely — feeding unsound eliminations into the solver loop, the puzzle rater, and the auto-difficulty pipeline. The rewrite enumerates row-based **and** column-based patterns, enforces a 3- or 4-digit base set, requires each target to contain every base digit, demands the two targets sit in different cross-lines and different non-base boxes of the JE band/stack, and validates the S-cell cover invariant (each base digit's S-cells must fit within two cover lines). Eliminations are limited to Bird's rule 1 — non-base candidates in the target cells — for which soundness follows directly from the cover invariant; the more aggressive rules 2-9 (mirror-node, double-JE, JE+) remain deferred. (#19)
- **An unreadable statistics history is no longer silently erased.** When the encrypted session-history file (`game_sessions.yaml`) could not be decrypted — e.g. after a hostname or `/etc/machine-id` change (the key is system-derived), or a partial read — `getAllSessions` treated it as empty and the next flush re-encrypted over it, destroying the entire history. Reads now fail closed, and the flush on exit refuses to overwrite a file it could not read, so the original bytes survive. The Statistics dialog detects the condition and offers to archive the file to `game_sessions.yaml.corrupt-<timestamp>` (the original is moved aside, never deleted) so a fresh history can start. Downstream packagers: a new `*.corrupt-<timestamp>` artifact may appear in the user data directory. (#26)
- **Saves, auto-saves, session history, and aggregate statistics are now written atomically.** These wrote directly over their target file (or, for aggregate stats, via a `rename` that never `fsync`'d), so a crash or power loss mid-write left a truncated, unloadable file — and since auto-save is the crash-recovery path, an interrupted auto-save could destroy the very game state it exists to protect. Writes now go to a `<file>.tmp`, are `fsync`'d to durable storage, then atomically `rename`d into place, so a reader always sees either the previous complete file or the new complete one. All four persistence paths share one crash-safe writer. (#25)
- **Importing statistics no longer corrupts the average-completion-time stat.** `importStats` recomputed each difficulty's average time *after* it had already added the imported game count into `games_completed`, so the local contribution was weighted by the post-merge total and divided by the same inflated total — the average drifted on every import and could never be repaired. The weighted mean is now computed from the pre-merge completion counts of each dataset, so importing identical data leaves the average unchanged and merging different datasets yields the correct weighted average. (#27)
- **Cumulative statistics counters widened to 64-bit.** `total_games`, `total_completed`, `total_moves`, `total_hints`, `total_mistakes`, the per-difficulty `games_played`/`games_completed`, and both win-streak counters were 32-bit `int` and could wrap at 2³¹ for very long-lived players, corrupting lifetime totals. They are now `int64_t`. The `aggregate_stats.yaml` schema is unchanged (YAML integers); existing files load unchanged and older binaries still parse the values within their former range. (#27)
- **A libsodium initialization failure no longer crashes the app on startup.** `EncryptionManager`'s constructor called `sodium_init()` and threw `std::runtime_error` on failure; because `SaveManager` and `StatisticsManager` built one unconditionally and `main()` has no top-level `catch`, an init failure (e.g. no `/dev/urandom` in a sandbox, or a seccomp policy blocking the RNG) terminated the process before the window appeared, with no user-facing diagnostic. `EncryptionManager` is now a stateless static utility that initializes libsodium lazily and reports failure as `EncryptionError::InitializationFailed` through the existing `std::expected` chain, so save/load degrades gracefully (the game still starts) instead of crashing. (#28)
- **`CompositeObserver` no longer unsubscribes unrelated subscribers on teardown.** `CompositeObserver::observe` discarded the per-callback unsubscribe token returned by `Observable::subscribe` and instead registered `Observable::clearSubscriptions()` as its teardown — so destroying one observer (or calling `unsubscribeAll()`) wiped **every** subscriber on that observable, not just its own. With both `MainWindow` and `TrainingWidget` owning a `CompositeObserver`, the first to subscribe to a shared observable would be silently torn down by the second's destruction, with no compile or test failure. `observe` now captures and stores the real per-callback token, so each subscription is released independently. (#30)
- **3D Medusa no longer produces unsound eliminations from non-bipartite coloring components.** The strategy 2-colors each strong-link component with a BFS, and already skipped the *elimination* rules (3-6) when the BFS detected an odd cycle (`is_bipartite=false`) — but the *contradiction* rules (1-2) ran first, unconditionally, on the same arbitrarily-colored nodes. For an odd cycle the A/B partition is a meaningless artifact of BFS visitation order, so "this whole color is false" could eliminate correct candidates, feeding bad eliminations into the solver loop, the difficulty rater, and training mode. The non-bipartite check now gates the contradiction rules as well, so such a component is skipped entirely. (Odd strong-link cycles do not arise on a uniquely-solvable puzzle, so well-formed boards are unaffected; this hardens the transient mid-solve case.) (#22)
- **Grouped X-Cycles now emits Type 2 (strong-strong) placements.** The cycle-closure handled only Type 1 (continuous loop) and Type 3 (weak-weak discontinuity) steps; a strong-strong discontinuity onto a single-cell node fell through with no step built, so the forced placement at that cell was never produced — the technique silently under-performed the non-grouped X-Cycles it claimed parity with, and the solver leaned on more expensive strategies / backtracking instead. The closure now mirrors the non-grouped `buildType2Step`, placing the digit at a single-cell discontinuity (a group node cannot be placed and is rejected). Additive and sound by construction — it reuses the proven non-grouped X-Cycles Type 2 logic with a group-rejection guard, is covered by dedicated regression tests, and the strategy-correctness replay reports no new wrong deductions; no eliminations change. Difficulty ratings of puzzles reachable via this pattern may shift accordingly. (#23)
- **Simple Coloring now applies Rule 2 (Exclusion) on a lone 2-cell conjugate pair.** `SimpleColoringStrategy` skipped every coloring component smaller than four cells, so the "Colour Trap" elimination on a single conjugate pair {X,Y} — where any cell seeing both X and Y can have the digit removed, since exactly one of the pair holds it — was never produced. This was a strict under-elimination: the solver was weaker than it should be, and the cheap Simple Coloring tier being skipped could inflate a puzzle's difficulty rating. The size guard is lowered from `< 4` to `< 2` (a 2-cell component); the contradiction rule (Rule 1) is inert below four cells, so the change only adds sound eliminations. (#23)
- **The `GameCommand` pipeline now honors every verb and gates on real preconditions.** `executeCommand`'s switch handled only 9 of the 16 `GameCommand` verbs — `NewGame`, `SaveGame`, `LoadGame`, `ValidateBoard`, `PauseGame`, `ResumeGame`, and `ClearNotes` fell through to a warning and silently did nothing — while `canExecuteCommand` returned `true` for every unhandled verb, so a button bound to `SaveGame`/`ResumeGame` appeared enabled then no-op'd (e.g. `ResumeGame` reported available with no game loaded). All verbs are now implemented (with a `GameCommandArgs` payload carrying the difficulty / save name / save id for the parameterized verbs), `canExecuteCommand` returns the real precondition per verb and fails closed for unknown values, and `MainWindow` dispatches new-game / save / load / undo / redo / toggle-mode through the pipeline instead of bypassing it. (#30)

### Platform support

- **Linux (Fedora)** — primary development platform; full interactive use by the maintainer.
- **Linux (Ubuntu 24.04)** — built and full test suite run in CI on every push.
- **Windows 10 1809+ and Windows 11, 64-bit** — installer artifact attached to the release. Built in CI on `windows-2025` (on demand); smoke-tested by the maintainer on Win11 before tagging, and the 1.0.0 installer was verified on a Windows 10 machine. The minimum version is Qt 6.8's; the installer enforces it.
- **Linux (openSUSE)** — RPM snapshots produced downstream via the openSUSE Build Service (not built directly by the project).
- **macOS** — not supported in 1.0; out of scope.

See [README.md](README.md#platform-support) for the difference between "tested", "CI-built", and "packaged downstream".

### Known limitations

- No user-facing timer pause. The timer runs continuously while a puzzle is open.
- Open sub-dialogs (Settings, Import Custom Puzzle, Find Step by Technique) do not re-translate when the language is changed from within them — close and reopen the affected dialog to see it in the new language. The main window shell (menu bar, toolbar, button panel, status bar) and the Training Mode widget retranslate immediately.
- No theme system; colors are fixed (light theme).
- Save file format v1.1 is the 1.0 stability boundary. Older v1.0 saves still load (the missing `PuzzleOrigin` field defaults to `Generated`). Pre-1.0 snapshot binaries may not load v1.1 saves; downgrading after upgrading is not supported.
